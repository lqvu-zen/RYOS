# RYOS behaviour map

`ARCHITECTURE.md`, `adr/` and `CLAUDE.md` say how RYOS is built. This file says
**what must keep working, and everywhere it shows up.** Most behaviours appear in
several places at once: normal rows, compact rows, favourite chips, the maximised
detail pane, select mode, scripts and pipelines, the window and the command line.
A change that reaches one place breaks the others unseen. (That is how compact mode
broke three times, select mode missed pipelines, and Quick Run lost "add as a new
script".)

Each entry is one line the user would recognise, **every surface** it appears on,
and the test that guards it, or **untested**.

## How to use it

- **Before you change an area, read its entries.** Check each surface listed, not
  only the one you are working on.
- **A fix adds or updates its entry and its test.** Put the issue number in the
  behaviour text, e.g. "(#27)".
- **A feature adds its entries** in the same change, with the surfaces it reaches.
- **Test names are exact.** Format: `test_ryos::<Class>::<test>` (a unit test in
  `tests/test_ryos.py`), `qt_smoke::<check>` (a check in `tests/qt_smoke.py`),
  `session_smoke::<step>` (a step in `tests/session_smoke.py`). A bare class name
  means every test in that class applies. `tests/test_cli.py`, `test_headless.py`,
  `test_agenttools.py`, `test_mcpserver.py` and `test_updates.py` are cited the same way.
  `release_check::<case>` is a case of `tests/release_check.py`, the release gate
  that runs on the built downloads (`release-ryos`), not in CI.
- **A smoke check usually opens one layout.** Where a check covers only some of the
  surfaces, the Guarded-by cell says which, e.g. "(N only)". The surfaces it does not
  name are unguarded, and the last section lists them.

## Surfaces

| Code | Surface |
| --- | --- |
| **N** | Normal (full-size) rows in the list |
| **C** | Compact rows (Options > Cards > Compact cards) |
| **F** | Favourite chips (the Favorites strip) |
| **A** | The All tab |
| **D** | The maximised layout: list on the left, detail pane, rail and Activity bar on the right |
| **S** | Select mode |
| **Sc** | Scripts |
| **P** | Pipelines (when an entry names both, it applies to both) |
| **R** | The Running list, the status bar and the Activity bar's running lines |
| **W** | The window as a whole (menus, dialogs, header, output panel) |
| **CLI** | `ryos-cli` / `ryos <command>`, headless |
| **MCP** | `ryos mcp`, what an AI agent sees |
| **T** | The tray icon, its menu and its tooltip |

## 17. Updates

Toolkit-free in `ryos/updates.py` (2.4 step 4). Since step 39 Offer release candidates (UP-31) lets the check, `version --check` and `update` read every release. Since step 5 the window downloads a newer release of its own zip in the background, and `ryos-cli version --check` reports whether it is downloaded and checked; since step 6 "checked" means `SHA256SUMS.txt` is signed with the build's release key (`ryos/signature.py`, `ryos/ed25519.py`) before the zip's hash counts, and `ryos-cli verify <zip>` checks a zip downloaded by hand. Until step 8 embeds the key, builds carry none and refuse to download. Applying an update comes in steps 9-10: since step 9 the swap itself is `ryos/swap.py`, run by the hidden `ryos-cli apply-update` from a copy outside the install; since step 10 the window's Restart to update and Help → Roll back, and `ryos-cli update [--rollback]`, decide when through `ryos/selfupdate.py` and start that helper. Each install keeps its own journal, lock, `previous.json` and at-next-start request in `updates\installs\<hash of its real path>\`. Since step 11 `release_check` updates and rolls back each frozen download end to end from a local signed source (UP-28...UP-30).

## Harness escapes

A process rule broken by a session (not a bug in RYOS) gets one line here: what happened, and the hook case or permission rule that now stops it. **A session that breaks a process rule adds, in the same change, the hook case or `deny` / `ask` rule that would have stopped it**, with its test in `tests/test_harness.py`; a new `deny` or `ask` rule needs Vũ's approval.

- 2026-10-09 (testing the MCP builds): a PowerShell `set APPDATA=…` set no environment variable, so test scripts ran against the real `%APPDATA%\RYOS`, landed in the real data and upgraded it to schema v10. Now `.claude/hooks/guard.py` refuses starting RYOS without pointing `APPDATA` elsewhere in the same command, a `set APPDATA=` outside `cmd /c`, and any write into the real folder; `test_harness::TestGuardRefuses`.
- 2026-10-13: a coding session reverted an uncommitted secretary edit to `docs/STATUS.md` / `docs/plans/`. Now `deny` rules stop `git checkout` / `git restore` on those paths and `git reset --hard`, and `guard.py` refuses whole-tree discards while they hold uncommitted changes; `test_harness::TestGuardRefuses`.
- PR #14 (v2.0.x): bumped `__version__` to 2.0.1 in a feature commit. Now CI's `harness` job fails any commit that changes `__version__` unless titled `Release candidate X.Y.Z-rcN` or `Release X.Y.Z`; `test_harness::TestVersionCheck`.
- 2026-10-08 to 2026-10-19: CI's qt-smoke failed in about half its runs (exit 139) and was re-run past for eleven days; the cause was the smoke's own exit on an unpinned PySide6 (6.12.0) that the shipped builds don't use. Now step 32's stop rule makes a session fix a red CI first, and the Qt smoke closes everything down before exit and fails if anything is left (`qt_smoke::close_down`).
- 2026-10-21 (v2.4.0-rc1): the candidate was published at 20:38 with no `release_check` run on record before it (the first recorded run is 20:50, after the publish, at a HEAD two commits past the build), and the step 12 row said "PASSED (29/0/0)" without one. Proposed, not yet in place (an `ask` rule changes with Vũ's approval): `release_check` writes `dist/release_check.passed` on a pass, holding HEAD, the hash of `SHA256SUMS.txt` and the case count; `guard.py` refuses `gh release create vX.Y.Z[-rcN]` unless that stamp names the current HEAD and the current `SHA256SUMS.txt` hash, with its test in `test_harness`.
