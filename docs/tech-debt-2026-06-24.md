# RYOS Technical Debt Review — 2026-06-24

_Snapshot at version 1.8.1 · 6,859 LOC across `ryos/` · 206 unit tests · CI: `test` + `gui-smoke` + `typecheck`._
_Supersedes the 2026-06-10 audit in `TECH_DEBT.md` (kept for history). Priority = (Impact + Risk) × (6 − Effort), each rated 1–5._

## Summary

The codebase is in good health and noticeably better instrumented than at the last audit: a UI-free `JobController` now owns the job lifecycle, CI runs a real-display GUI smoke job and a scoped `mypy` job alongside the unit suite, and a source-integrity guard protects against the file corruption seen during recent work. Dependency surface is still a single pinned package, there are **zero** `TODO`/`FIXME` markers, and exception handling in the core (`notifications.py`, `settings.py`, DB paths) is narrowed and logged.

The debt that remains is concentrated where it was before — **`ryos/ui/app.py`** — and it has quietly regrown: the multi-monitor and search features landed on top of the god class, pushing it to **2,574 lines / 107 methods** and re-inflating `_refresh_cards` to **219 lines**. None of this is on fire, but the UI layer is the most-changed, least-tested, hardest-to-review part of the system, and that is exactly where new features keep landing.

## Findings

### 1. UI/app pure logic untested — Priority 24
The suite (206 tests) covers the core thoroughly, but the logic that has grown most recently lives inside `RYOSApp` widget methods: search filtering (`_apply_search_filter`, `_update_search_hint`), section visibility (`_update_section_visibility`, 86 lines), and the multi-monitor glue around `screens.relocate_geometry`. The pure `screens.relocate_geometry` is already tested — proof the pattern works — but its callers in `app.py` are not.
**Justification:** This is the freshly-changed, user-facing logic where regressions ship. Extracting each decision into a UI-free helper (as was done for `quickrun`, `jobs`, `runner`, `job_controller`) and unit-testing it is low-to-medium effort and pays off on every future search/layout change.

### 2. Giant methods regrew — Priority 21
`_refresh_cards` is back to **219 lines** (it had been trimmed to 138) and `_build_quick_run_bar` is 138; both mix layout, state, and event wiring in one scope. The search/filter work re-inflated them.
**Justification:** These are the methods most likely to break when touched and the hardest to review. Splitting them into named sub-builders (per section / per card type) — the same move applied successfully before — makes diffs reviewable and is the natural companion to item 1.

### 3. `TECH_DEBT.md` is stale — Priority 20
The root `TECH_DEBT.md` still cites "app.py 2,380 lines", "50 tests", and lists the JobController/CI/`screens.py` work as not-done. It now actively misrepresents the codebase.
**Justification:** A debt register that lies is worse than none — it misdirects effort. Cheap to fix: replace it with this review (or fold this in) and keep the old one as dated history.

### 4. Broad `except` audit — Priority 15
Twelve broad `except Exception` / bare guards remain, across `db.py`, `runner.py`, `screens.py`, `app.py`, `cards.py`, `dialogs.py`, `theme.py`, `widgets.py`, `__main__.py`. Many are deliberate "optional feature, never crash" cosmetics (toast/tooltip/theme, win32 monitor queries) and should stay; a subset in the data/run paths may be hiding real errors.
**Justification:** `notifications.py` was just narrowed with success; the same pass over `db.py`/`runner.py`/`screens.py` would convert "it silently stopped" reports into actionable logs. Scope is small because most guards are intentional and stay as-is.

### 5. `dialogs.py` untested — Priority 12
At 1,219 lines (second-largest module) with builders like `_build` (101) and the tabbed Advanced Options dialog, `dialogs.py` has no unit coverage.
**Justification:** Dialogs encode validation and settings-mapping logic worth testing, but much is genuinely widget construction. Extract the validation/mapping cores opportunistically when touched; don't rewrite wholesale.

### 6. `gui-smoke` is shallow — Priority 12
The new CI GUI smoke drives a script run and a stop, which already caught a real Linux startup crash. It does not yet exercise pipelines, group switching, drag-and-drop, or the Quick Run bar in the live app.
**Justification:** Each path it doesn't cover is a widget path no test reaches. Adding a pipeline-run and a group-switch scenario is medium effort and broadens the only real-display safety net.

### 7. `RYOSApp` god class — Priority 9 (root cause)
A single class owns window setup, drag-and-drop, tab/group CRUD, the Quick Run subsystem, search, multi-monitor placement, output routing, and update checks — **2,574 lines, 107 methods**. It scores mid-table only because a full split is high-effort and risky.
**Justification:** This is the root cause behind items 1, 2, and 6. The proven path is incremental extraction (the JobController increments landed cleanly with the suite green at each step). Next candidate seams: search/filter state, the tab/group controller, and drag-and-drop. Do it opportunistically as each area is touched — never as a big-bang.

### 8. `mypy` gap — Priority 8
`mypy` now checks 13 files (core + the type-clean UI modules) but `app.py`, `dialogs.py`, and `cards.py` are excluded due to Tk's dynamic-widget false positives.
**Justification:** Real but low-leverage: closing it means scattering `# type: ignore[arg-type]` across widget calls for little payoff. Worth doing only as those files are refactored under items 1–2 anyway.

## What's healthy (don't "fix")
- Thin, standard-library-only runtime (just `tkinterdnd2`, pinned) — minimal dependency debt.
- Strong core test culture (206 tests) covering DB, interpreter, quickrun, jobs, runner, job_controller, settings, version parsing, and source integrity.
- Thread-safe output via `Queue` + `after()` polling, now behind the tested `JobController.pump()`.
- CI gates every push: lint, unit suite (Ubuntu + Windows × 3.10/3.13), real-display GUI smoke, and scoped type-check.
- Zero `TODO`/`FIXME` debt markers; narrowed-and-logged exception handling in the core.

## Resolved since the 2026-06-10 audit
- **Job lifecycle (old item #6):** extracted into UI-free `job_controller.JobController` (allocation, capacity, pipeline stepping, completion, drain) across three ADR-0001 increments, with 18 unit tests.
- **GUI smoke:** `gui-smoke` CI job runs the real `RYOSApp` under Xvfb; caught a Linux `.ico` startup crash on its first run.
- **Type-check:** `mypy` CI job over the UI-free core + clean UI modules (13 files).
- **Source integrity:** a unit guard scans shipped source for NUL bytes, bad UTF-8, and merge-conflict markers.
- **Exception handling:** `notifications.py` broad catches narrowed to real types and logged.

- Audit the 12 broad `except` guards; narrow the data/run-path ones in `db.py`/`runner.py`/`screens.py`, leave the deliberate cosmetics (item 4).

- Add a pipeline-run and a group-switch scenario to `gui-smoke` (item 6).

**Phase 3 — Structural (ongoing, only as you touch each area)**
- Peel the next cohesive subsystem off `RYOSApp` — search/tab/drag controllers — one at a time, suite green at each step (item 7).
- Fold each newly-extracted, now-clean module into the `mypy` scope as it lands (item 8).
- Extract `dialogs.py` validation/mapping cores opportunistically (item 5).
