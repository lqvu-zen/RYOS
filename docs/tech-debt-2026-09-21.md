# RYOS Technical Debt Review — 2026-09-21

_Snapshot at version 1.11.2 · 11,628 LOC across 30 modules in `ryos/` · 652 unit tests + 16 GUI smoke checks · CI: `test` + `gui-smoke` + `typecheck`._
_Supersedes `docs/tech-debt-2026-06-24.md` (kept for history). Priority = (Impact + Risk) × (6 − Effort), each rated 1–5._

## Summary

The three months since the last audit were the most productive stretch in the project's history and also the most debt-neutral: **67 commits, +9,511 / −450 lines across `ryos/` and `tests/`**, and the test suite grew faster than the code — **237 → 652 unit tests** against **6,989 → 11,628** package lines. Seven new pure modules were extracted rather than bolted onto the god class (`scheduling`, `history`, `search`, `grouping`, `dragdrop`, `screens`, `ui/placement`), and the GUI smoke net went from 2 checks to 16, now covering pipelines, drag-and-drop, schedules, run history, output search and card layout.

Most of the June register is genuinely closed. `_refresh_cards` went 219 → 46 lines and stayed there. The broad-`except` concern is resolved outright: the raw count rose 12 → 22, but **every one of the 22 is deliberate** — audited individually for this review, they either re-raise (`db._connect`, `__main__`), surface to the user (`runner`, export/import), or guard a genuinely optional subsystem (tray, win32 monitor queries, the schedule timer). Discipline held while the count grew.

What did not move is the thing that did not move last time either: **`ryos/ui/app.py` grew 23%, from 2,559 to 3,145 lines and 145 methods**, and the `SearchController` extraction the June audit named as the next step was never done. Every feature this quarter landed on top of the god class. That file plus `dialogs.py` (1,219 → 1,864 lines, still zero unit tests) is 43% of the package.

The highest-value item this time is new and cheap: **mypy sees only 39% of the codebase**, and the blind spot now includes 1,128 lines of UI-free core that has no Tk excuse at all.

## Findings

### 1. `mypy` checks 39% of the codebase — Priority 35

The scope is 20 of 30 modules, but line count tells the real story: **7,187 of 11,628 lines (61%) are unchecked**. The June audit framed this as a Tk problem, and for `app.py`, `dialogs.py`, `cards.py` and `theme_editor.py` it still is. But the blind spot has since grown to include modules with no widget code at all:

| Unchecked core module | Lines | State today |
| --- | ---: | --- |
| `themes.py` | 692 | **passes mypy clean, unmodified** |
| `startup.py` | 68 | **passes mypy clean, unmodified** |
| `single_instance.py` | 185 | 2 errors, both real `Optional` narrowing |
| `tray.py` | 183 | 1 error, the guarded-optional import pattern |

I ran these to confirm rather than assume. `themes.py` and `startup.py` can join the scope **today, with zero code changes** — 760 lines, including all the colour maths every widget depends on. The other two need three small fixes between them.

**Justification:** This is the cheapest real win on the board. The June audit was right that chasing `app.py` into mypy means scattering `# type: ignore` for little payoff — but that argument never applied to `themes.py`, which got excluded only because the scope list was never revisited as new core modules landed. mypy also earns its keep here: it caught a genuine slip in `pipeline.py` during the issue #7 work, in a file that *is* in scope.

### 2. Quick Run has no live coverage — Priority 28

`quickrun.py` is well-tested as pure logic (path containment, ranking, parsing). The **bar itself has zero coverage**: `_build_quick_run_bar` is 137 lines — flagged at 138 in the June audit and untouched since — and none of the 16 GUI smoke checks touches the bar (the only `quick` in `tests/gui_smoke.py` is a comment about a fast-finishing job), while those checks now cover pipelines, schedules, drag-and-drop, run history and output search.

**Justification:** It is now the only major subsystem with no end-to-end check, which makes it the most likely place for the next silent regression. Three of this quarter's four reported issues (#2, #3, #6) were widget-layer regressions that unit tests structurally could not catch, and each was closed by adding a smoke check. The same move applies here. Splitting the 137-line builder is the natural companion, and the sub-builder pattern that took `_refresh_cards` from 219 to 46 lines is proven in this codebase.

### 3. `handle_step_done` is 156 lines — Priority 28

`job_controller.py` is the best-tested module in the project and the one whose bugs are hardest to reason about — concurrent groups, retries, failure policy, conditional steps, launcher release. `handle_step_done` now carries all five concerns in one scope, at 156 lines and roughly a third of the module.

**Justification:** Giant methods are least excusable here, because this module is UI-free and trivially testable — there is no Tk friction to justify the size, unlike the builders in `app.py`. This is also where the subtlest bugs of the quarter lived: the lazy head-only skipping fix and the settle-then-mark ordering in `release_launcher_step` were both order-of-operations bugs inside this dispatch path. Named sub-steps (retry, group settle, failure policy, advance) would make the ordering legible and each branch directly testable.

### 4. `pystray` / `pillow` are declared hard but coded optional — Priority 20

`pyproject.toml` lists both as unconditional runtime dependencies. `tray.py` treats them as entirely optional: a guarded import, an `_AVAILABLE` flag, every entry point a no-op when missing, and a `TestTrayWithoutPystray` case that exercises the absent path. `pillow` is imported by exactly one module (`tray.py`) for exactly one purpose (the tray icon image).

The two declarations contradict each other. Either the optionality in the code is dead weight, or the dependencies belong in an extra:

```toml
[project.optional-dependencies]
tray = ["pystray>=0.19,<1.0", "pillow>=10,<12"]
```

**Justification:** Small but worth closing, because the mismatch already cost real time: CI ran `--no-project`, so `pystray` was genuinely absent there while present locally, and a tray test passed locally while **CI sat red for five commits** before anyone noticed. Resolving the ambiguity deliberately — rather than leaving two sources of truth — is what prevents the repeat. It also retires the June audit's "standard-library-only runtime (just `tkinterdnd2`)" health claim, which the tray work quietly voided.

### 5. `dialogs.py` — 1,864 lines, no unit tests — Priority 12

Up 53% from 1,219 in June, now 10 classes and 84 functions, with `_build` at 133 lines and `_build_appearance_tab` at 105. The string `dialogs` appears once in the entire unit suite.

**Justification:** Unchanged from June, and the reasoning still holds: much of this file is genuine widget construction that unit tests would only calcify. The settings-mapping and validation cores are the parts worth extracting, and they are worth extracting *when the surrounding code is already being touched* — not as a dedicated campaign.

### 6. `RYOSApp` god class — 3,145 lines, 145 methods — Priority 8 (root cause)

One class owns window setup, drag-and-drop, tab and group CRUD, Quick Run, search, multi-monitor placement, output routing, the schedule tick, run-history pruning and update checks. It grew 23% this quarter; the `SearchController` extraction named as the next step in June was never started.

Notably, the *method-level* debt is fine — only 7 methods exceed 50 lines and the largest is `__init__` at 148. This is not giant-method debt any more; it is a count-of-responsibilities problem.

**Justification:** It scores low only because a full split is high-effort and high-risk, and that ranking is a statement about sequencing, not importance — it is the root cause behind items 2, 5, and much of 1. The incremental path is proven twice over in this repo (the `JobController` increments, then seven pure modules this quarter), and it works precisely because each extraction was small and kept the suite green. The honest lesson from this quarter is that opportunistic extraction did *not* happen on its own: seven modules were carved out for *new* logic while the existing god class kept growing. If `app.py` is to shrink, one extraction needs to be scheduled deliberately rather than hoped for.

## What's healthy (don't "fix")

- **Test culture outpaced the code.** 237 → 652 unit tests against a 66% LOC increase; the suite runs in ~14s.
- **New logic lands as pure modules.** Seven UI-free modules extracted this quarter, each unit-tested, each with a real display-free test story.
- **Exception discipline held.** All 22 broad guards are deliberate: re-raise, surface, or guard an optional subsystem. Audited individually for this review.
- **Zero `TODO` / `FIXME` / `XXX` / `HACK` markers**, still.
- **Three CI gates on every push** — lint, unit suite (Ubuntu + Windows × 3.10/3.13), real-display GUI smoke, scoped type-check.
- **Regression tripwires are now a habit**: `TestRowWidthsArePinned` for widened accessor rows, `TestDocsMatchTheCode` for doc drift, and smoke checks added for each reported issue.
- **The release runbook holds a hard CI gate** and the exe smoke test asserts the version in the window title.

## Phased remediation plan

Designed to run **alongside feature work**, not as a freeze.

**Phase 1 — Reclaim the type-check (≈1 hour)**
- Add `themes.py` and `startup.py` to `[tool.mypy]` — no code changes needed (item 1).
- Fix the 2 `Optional` narrowings in `single_instance.py` and the 1 guarded-import error in `tray.py`, then add both (item 1).
- Decide `pystray`/`pillow`: optional extra, or drop the in-code guards. One source of truth (item 4).

**Phase 2 — Close the coverage gap (≈half a day, opportunistic)**
- Add a Quick Run scenario to `gui-smoke`, and split `_build_quick_run_bar` into named sub-builders while there (item 2).
- Decompose `handle_step_done` into named sub-steps; the branches are already individually tested, so this is refactoring under a net (item 3).

**Phase 3 — Structural (schedule it; do not wait for an excuse)**
- Extract `SearchController` from `RYOSApp` as its own focused pass — the one item that has now been deferred twice (item 6).
- Fold each newly-clean module into the `mypy` scope as it lands, and keep the scope list under review when new modules appear — that omission is what created item 1.
- Extract `dialogs.py` validation/mapping cores opportunistically when touching them (item 5).
