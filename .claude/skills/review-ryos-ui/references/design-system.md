# Lens 4: design system (tokens, states, consistency)

Adapted from the `design:design-system` skill (audit mode) and the typography
and semantic-colour sections of `qt-development-skills:qt-ui-design`.

## The tokens RYOS has

| Kind | Source of truth | Notes |
| --- | --- | --- |
| Colour | Palette keys (`ryos/themes.py`, `ryos/presets/*.json`) | Built from 7 seed colours by `build_palette()`; every theme defines every key |
| Legible text colours | `drawn_colors()` in `ryos/qtui/stylesheet.py` | Checked across every shipped theme by `DRAWN_PAIRS` in the unit suite |
| Spacing | `cardstyle.CARD_PADDING`, `ROW_METRICS`, `CHIP_PADDING` | Rows share one table; dialogs use layout defaults |
| Sizes | `cardstyle.RUN_DIAMETER`, `CHIP_RUN_DIAMETER`, `cards.BUTTON_WIDTH` | |
| Radius | 4 px panels, 3 px controls, 2 px badges; pills are half their height | From `design-system/build.py` |
| Icons | `ryos/qtui/icons.py` `SHAPES`, tinted by `role_colors()` | One style; `check_one_icon_set` in qt_smoke fails on a glyph or emoji in button or menu text |
| Type | Segoe UI, base 10pt in the stylesheet | Sizes are set per rule; there is no named scale yet |

The design system itself (`design-system/project/`, generated by
`design-system/build.py`) documents these; `build.py --check` keeps it in step
with the code.

## What to audit

The audit script reports the first two; read the code for the rest.

- **Hard-coded colours** in `ryos/qtui/*.py`. Each should be a palette key or
  a `drawn_colors()` entry, so it follows the theme. A new colour role means
  a new key in `themes.py` (every theme gets it) -- never a hex in a widget.
- **The type scale.** Count the distinct font sizes. A calm interface uses
  three or four per screen (e.g. 8pt caption, 9pt secondary, 10pt body,
  13–16pt titles). Map each size in use to a role; sizes with no clear role
  are findings. A single scale in `stylesheet.py` (named sizes) is the fix.
- **States per component.** For each control type (primary button, quiet
  button, pill, row, chip, input, check box), check default, hover, pressed,
  focus, disabled and -- where it applies -- selected and error are all
  defined and look like one family. Missing focus and disabled states are the
  usual gaps.
- **Semantic colour roles.** Interactive colour (the accent) must not also
  be decoration; red means failure or danger only; green means run or OK
  only.
- **Per-widget stylesheets.** `setStyleSheet` on one widget is allowed where
  its colour depends on its own state (Run/Retry, a row's highlight colour).
  Anywhere else it should be an object-name rule in `stylesheet.py`.
- **Consistency across screens.** The same thing looks the same in the main
  window, the maximised pane and the dialogs: the Run button, the star, a
  primary button, a list panel.
- **Documentation drift.** Does `design-system/project/README.md` still
  describe what the app draws? Note what to update.

## Output for this lens

Findings tagged `[system]`. Include a short token-coverage table (colours
