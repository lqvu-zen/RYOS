# RYOS Tutorial Generator

This skill produces the **end-user guide in `docs/tutorial/`**: one Markdown page per
topic, each step backed by a real screenshot of exactly what the reader will see.

**What's on screen is the source of truth.** The UI moves faster than prose; every claim
in a page must match a screenshot or the code, never an older page.

## How screenshots are made

`scripts/capture.py` builds the real window through the run-ryos driver and walks the
guide in reading order:

```bash
uv run python .claude/skills/ryos-tutorial-generator/scripts/capture.py
```

- **Off screen.** Windows, dialogs and menus render with `WA_DontShowOnScreen`; nothing
  appears on any monitor. Never drive the user's real desktop or put a window on their
  primary screen.
- **Throwaway data.** APPDATA points at a temp folder loaded with the repo's `samples/`
  (a *Samples* group, ten scripts, three pipelines) plus an empty *Tools* group. The
  user's own database is never read or written.
- **Only RYOS in every image,** by construction: each shot is a grab of a RYOS widget,
  so no desktop, taskbar or other app can leak in.
- **Light theme, 560×780**, the maximised shots at 1280×760; images land in
  `docs/tutorial/images/` as `NN-name.png`, sorted in reading order.

Each image is taken through the window's own hooks: `win.run_dialog` catches a dialog
(fill it, grab it, cancel it), `win.popup` catches a right-click menu, `card(...)
.set_hovered(True)` shows a row's hover buttons, `set_workspace(True)` the maximised
layout. To add a step, add a few lines in the right section of `capture.py` and link the
new name from the page.

## The workflow

1. **Capture.** Run the script. It prints every image it saved.
2. **Look at every image** with `Read` before writing about it. A shot that shows the
   wrong state (a crop that missed the thing, a dialog not filled in) gets fixed in
   `capture.py` and recaptured -- never described around.
3. **Check the words against the code.** Button labels, menu entries, option names and
   choices come from the rule modules (`cardmenu.py`, `sections.py`, `outputpanel.py`,
   `settings_schema.py`, `pipelinesteps.py`, `scheduleform.py`, `selection.py`, ...).
   Quote them exactly.
4. **Write the pages** (structure below), one per topic, prose and images together.
5. **Check the set**: every link and image resolves, no image is unused, pages read in
   order with previous/next links. A short script over `docs/tutorial/*.md` does it.
6. **Report drift and rough edges** you found on the way: places the old pages were
   wrong, and anything in the UI that looked off (a label showing a raw value, a button
   that looks disabled when it isn't) -- those are for the user to decide on.

Keep the user in the loop before deleting pages or images from a previous run; say which
are replaced. Git keeps the old ones.

## Page set

```
docs/tutorial/
├── README.md                      index: intro + linked contents
├── 01-main-window.md              header, search, pills, sections, rows, hover buttons, row menu
├── 02-adding-a-script.md          drop files; the script dialog
├── 03-running-and-output.md       Run, Running list and Stop, OK / Failed / Retry, output panel
├── 04-groups.md                   pills, new group, the group menu, moving rows
├── 05-parameters-and-presets.md   parameters, presets and the row's preset chip, ask each run
├── 06-pipelines.md                the editor, step settings, running one
├── 07-schedules-and-history.md    schedule dialog, run history
├── 08-quick-run.md                the Quick Run box
├── 09-maximised-layout.md         list + detail
├── 10-import-export.md            File menu, import choices
├── 11-settings.md                 Options menu, Options tabs, Appearance
├── 12-tips.md                     compact rows, select mode, dark theme, small things
└── images/                        generated by capture.py
```

Keep numeric prefixes contiguous; update `README.md`, the root `TUTORIAL.md` chapter
list and the README's "How to Use" table when pages change.

## Writing

Each page: an H1, a sentence of context, the steps, and a
`← previous · Contents · next →` line at the bottom. Address the reader as "you", name
buttons exactly as they appear (with their glyphs: **▶**, **↻**, **✎**, **☆**), and keep
each step to what the reader does and what they see. Alt text describes the image for
someone who can't see it. Short paragraphs and the occasional small table beat walls of
bullets.

`references/ryos-screen-map.md` lists each screen, how the capture script reaches it, and
the sample data -- read it before editing `capture.py`.
